# WelLink 추천·성분 점검 엔진

WelLink 앱의 **③ 구성 선택 → ④ 성분 점검** 단계를 담당하는 서버 모듈입니다.

- **입력**: 나이·성별, 건강 관리 목적, 가족력, 복용 중인 약, (선택) 알레르기·흡연·임신/수유, 지금 먹고 있는 제품(타사 제품 포함, 표시사항 그대로)
- **출력**
  1. 플랫폼 제품으로 만든 **추천 조합**과 제품별 추천 이유(식약처 기능성 문구), 대체 제품
  2. 조합 전체의 **성분 분포**(성분별 하루 합계, 권장·상한 대비 %)
  3. **점검 결과**: 과다 · 중복 · 부족 · 복용 약과의 병용 주의 · 건강기능식품끼리의 병용 주의 · 개인 상태(흡연·임신·알레르기)에 따른 주의. 항목마다 **근거**(기준치 출처, 제품 표시 함량, 규칙 근거)가 붙습니다.
  4. **수정안**: 항목별 수정안(빼기·바꾸기·섭취량 줄이기·추가·시간 나누기)과, 위험도가 높은 항목부터 차례로 고친 **자동 수정안**
  5. 시간 간격이 필요한 성분을 나눈 **섭취 시간표**(아침/점심/저녁)

S파트 설계 원칙을 그대로 코드에 반영했습니다.

| 설계 원칙 (S파트) | 구현 |
|---|---|
| 안전 점검은 규칙 기반, AI 판단에 맡기지 않음 | 성분 합산·상한 비교·병용 판단은 모두 규칙과 기준 데이터로 계산합니다. 생성형 AI는 쓰지 않습니다. |
| 점검은 근거와 함께 | 모든 점검 항목에 `evidence`(출처·내용)를 붙입니다. |
| 추천은 돕고 선택은 사용자가 | 추천 → 사용자가 빼기/바꾸기/고정 → `/v1/checks`로 재점검합니다. 고정(`locked`)한 제품은 수정안에서 건드리지 않습니다. |
| 질병 표현 금지 | 추천 이유는 식약처 기능성 표시 문구로만 씁니다. 모든 결과에 상담 안내 문구를 넣습니다. |
| 입력은 단계적으로 | 필수 입력은 나이·성별·목적뿐이고 나머지는 선택 입력입니다. |
| 민감정보 보호 | 서버는 건강 정보를 저장하지 않습니다(요청마다 계산하고 버림). |

> ⚠️ **데이터는 개발용 시드 값입니다.** 영양소 기준치, 기능성 원료 일일섭취량, 병용 규칙, 제품 정보는 출시 전에 대표자 검수와 자문 약사·영양사 검토를 거쳐야 합니다. 아래 [검수가 필요한 데이터](#검수가-필요한-데이터)를 참고하세요.

### 건강 관리 목적

초기 앱에는 일반 소비자가 많이 찾는 **핵심 목적(core)** 만 보여 주고, 고령층·특정 소비층용 **확장 목적(extended)** 은 데이터에만 두었다가 나중에 노출합니다. 엔진은 두 종류를 모두 처리합니다(`/v1/catalog/goals?tier=core`).

| 구분 | 목적 |
|---|---|
| 핵심 | 피로 개선, 면역력 관리, 체중(체지방) 관리, 항산화·관절 관리, 기초 체력·영양 보충, 장 건강, 눈 건강, 혈행·혈중 지질 관리 |
| 확장 | 뼈 건강, 관절 건강, 간 건강, 혈당 관리, 스트레스·긴장 완화, 기억력 관리 |

**"염증 조절" 수요는 '항산화·관절 관리'로 받습니다.** 건강기능식품에는 염증 개선 기능성이 인정되지 않아, 화면에 '염증'처럼 질병과 관련된 표현을 쓰면 표시·광고 기준에 걸릴 수 있습니다. 그래서 인정된 기능성(유해산소로부터 세포 보호, 관절·연골 건강)으로만 안내합니다. 목적 이름은 `goals.json`에서 바꿀 수 있습니다.

### 표시 단위·섭취 횟수 정규화

제품마다 함량 표시 방식이 달라도 **표시사항 그대로** 넣으면 됩니다. 엔진이 모든 값을 **1일 기준 · 성분별 같은 단위**로 바꾼 뒤 합산하고 비교합니다.

- 단위: IU(비타민A·D·E), g/mg/μg(mcg), CFU/억CFU
- 함량 기준: 1일 섭취량당(`per_day`) 또는 1회 섭취량당(`per_serving`) × 표시된 1일 섭취 횟수
- 실제 섭취: 표시와 다르게 먹으면 `actual_servings_per_day`(예: 1일 2회 제품을 1회만)로 반영
- 결과의 `distribution[].sources[].calculation`과 점검 근거에 환산 과정을 남깁니다(예: `1회 500IU × 1일 2회 = 25μg → 실제 1일 1회 섭취(표시의 0.5배) = 12.5μg`). IU로 익숙한 성분은 `total_iu`도 함께 줍니다.

## 빠른 실행

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements-dev.txt

# 테스트
.venv/bin/python -m pytest -q

# API 서버 + 데모 화면
.venv/bin/uvicorn wellink_engine.api:app --reload
#  - 데모 화면:  http://localhost:8000/      (모바일 화면 크기의 시연 페이지)
#  - API 문서:   http://localhost:8000/docs  (앱 개발사 연동용 OpenAPI)
```

데모 화면은 연동 흐름을 보여 주는 참고용 프로토타입입니다. 실제 앱(Flutter 또는 React Native)은 같은 API를 호출하면 됩니다.

## API

| 메서드 | 경로 | 용도 |
|---|---|---|
| POST | `/v1/recommendations` | 프로필과 현재 제품으로 추천 조합을 만들고, 점검 결과와 수정안을 함께 반환 |
| POST | `/v1/checks` | 사용자가 수정한 조합을 점검하고 수정안 반환 |
| GET | `/v1/catalog/goals` | 건강 관리 목적 목록 |
| GET | `/v1/catalog/family-history` | 가족력 항목 목록 |
| GET | `/v1/catalog/products?platform_only=true` | 제품 목록 (성분·기능성·주의사항 포함) |
| GET | `/v1/catalog/drugs?q=와파` | 약 이름 검색 (복용 약 입력 자동완성) |
| GET | `/v1/catalog/ingredients?q=비타민` | 성분 검색 (타사 제품 직접 입력용) |

### 앱 연동 흐름

```
① 프로필 입력 ──► POST /v1/recommendations
                    └─ recommended[], combination[], report, revision
② 사용자가 조합 수정 (빼기 / 대체 제품으로 바꾸기 / 고정 / 수정안 '적용')
③ 수정한 combination ──► POST /v1/checks ──► report, revision
   (②~③ 반복. revision.items는 그대로 /v1/checks에 다시 보낼 수 있음)
④ 확정한 조합으로 주문·QR 발급 (주문 API는 별도)
```

### 요청 예시

```json
POST /v1/recommendations
{
  "profile": {
    "age": 34, "sex": "male",
    "goals": ["bone", "cardio"],
    "family_history": ["dyslipidemia"],
    "medications": ["아스피린"],
    "allergies": [], "smoker": false, "pregnant_or_lactating": false
  },
  "current_products": [
    {"product_id": "ext_multi"},
    {"name": "해외직구 비타민D", "ingredients": [{"name": "Vitamin D3", "amount": 2000, "unit": "IU"}]}
  ],
  "max_products": 3
}
```

`goals`는 중요한 순서대로 보냅니다. 첫 번째 목적의 가중치가 가장 높습니다. 타사 제품은 `product_id`로 등록 제품을 고르거나, 제품명과 표시 성분(1일 섭취량 기준)을 직접 넣습니다.

### 응답에서 화면에 쓰는 필드

| 필드 | 화면 |
|---|---|
| `report.summary` | 결과 상단 배너(`overall_label`)와 칩(과다 n · 중복 n · 부족 n · 병용 주의 n …) |
| `report.findings[]` | 점검 결과 카드. `severity`(avoid > warning > caution > info), `title`, `message`, `guidance`, `evidence[]`, `suggestions[]` |
| `report.distribution[]` | 성분 분포 막대. `total`, `percent_of_reference`(권장·최소 대비), `percent_of_upper`(상한·최대 대비), `status`, `sources[]`(제품별 함량) |
| `report.goal_coverage[]` | 목적별 충족 여부 |
| `report.schedule` | 섭취 시간표(알림 설정에 사용) |
| `recommended[].reasons / alternatives` | 추천 이유, '다른 제품으로 바꾸기' 목록 |
| `excluded[]` | 추천에서 뺀 제품과 이유(예: 복용 약과 병용 주의) |
| `revision` | 자동 수정안 단계, 적용 전·후 요약, `items`(적용 결과 조합) |

## 판단 로직

### 점검 (checker.py)

조합의 모든 제품에서 성분 함량(1일 섭취량 × `servings`)을 더한 뒤 판단합니다.

| 분류 | 유형 | 기준 | 심각도 |
|---|---|---|---|
| 과다 | `excess` | 영양소: 상한섭취량(UL) 초과 / 기능성 원료: 고시 일일섭취량 최대 초과 | 조정 권장 (원료별 설정 가능) |
| 과다 | `near_upper` | 상한섭취량의 80% 이상 (식사 섭취분을 더하면 넘을 수 있음) | 주의 |
| 중복 | `duplicate` | 같은 성분을 2개 이상 제품에서 섭취(합계는 기준 안). 제품 묶음별로 하나로 모아서 알림 | 참고 |
| 부족 | `below_effective` | 기능성 원료 합계가 고시 일일섭취량 최소에 못 미침 | 주의 |
| 부족 | `goal_gap` | 고른 목적을 채우는 기능성이 조합에 없음 | 참고 |
| 부족 | `nutrient_low` | 우선 확인 영양소(목적·가족력·생애주기·약물 고갈)의 보충량이 권장량의 30% 미만 | 참고 |
| 병용 주의 | `drug_interaction` / `drug_timing` | 복용 약 약효군 × 성분 규칙 (예: 와파린 × 비타민K, 스타틴 × 홍국, 갑상선호르몬제 × 칼슘) | 규칙별 |
| 병용 주의 | `supplement_interaction` / `supplement_timing` | 성분끼리의 규칙 (예: 칼슘 ↔ 철 시간 간격, 출혈 경향 원료 2가지 이상) | 규칙별 |
| 섭취 주의 | `profile_caution` / `allergy` | 흡연 × 베타카로틴, 임신·수유 × 홍국·가르시니아 등, 알레르기 원료 | 규칙별 |
| 확인 필요 | `unknown_drug` / `unknown_ingredient` | 인식하지 못한 약이나 성분은 **'문제없음'으로 처리하지 않고** 약사 확인을 안내 | 주의 |

- 영양소 기준치는 나이·성별 구간(19–29, 30–49, 50–64, 65–74, 75+)별로 고릅니다.
- 마그네슘처럼 상한이 보충제에만 적용되는 성분은 따로 표시합니다(`ul_basis: supplement_only`).
- 식사로 섭취하는 양은 합계에 포함하지 않습니다. 화면 안내 문구에도 이 점을 넣었습니다.

### 추천 (recommender.py)

1. 목적을 기능성 태그 필요도로 바꿉니다. 목적 순서에 따라 1.0, 0.85, 0.7 … 가중치를 주고, 가족력 관련 목적은 더 낮은 가중치로 더합니다.
2. 제품의 기능성은 **표시 요건을 채울 때만** 인정합니다. 영양소는 1일 섭취량이 영양성분 기준치의 30% 이상, 기능성 원료는 고시 일일섭취량 최소 이상이어야 합니다. 그래서 추천 이유는 그 제품이 실제로 표시할 수 있는 문구로만 나옵니다.
3. 이미 먹는 제품이 채운 기능성은 '충족'으로 봅니다. 예를 들어 오메가3를 이미 먹고 있으면 혈행 목적에 오메가3를 또 추천하지 않습니다.
4. 후보 제품을 조합에 넣어 **실제로 점검을 돌려 본 뒤**, 아래 경우는 제외하고 `excluded[]`에 이유를 남깁니다.
   - 조정 권장 이상의 문제가 생기는 경우
   - 복용 약·개인 상태·알레르기와 관련된 주의 항목이 생기는 경우. 이런 제품은 엔진이 먼저 권하지 않고, 사용자가 직접 추가하면 점검으로 알려 줍니다.
5. 남은 후보 중 '필요도를 가장 많이 채우면서 감점(가격, 시간 간격, 중복)이 적은' 제품을 하나씩 고릅니다. 효용이 기준보다 작으면 멈춰서 조합을 가볍게 유지합니다.

### 수정안 (reviser.py)

- **항목별 수정안**: 각 점검 항목에 대해 빼기·바꾸기·섭취량 줄이기·추가 후보를 만들고, 적용 후 다시 점검해서 **그 항목이 실제로 해결되는 것만** 보여 줍니다. 각 수정안에는 새로 생기는 항목(`introduces`)과 하루 가격 변화도 함께 담깁니다.
- **자동 수정안**: 조합 점수를 매기고, 점수가 가장 많이 좋아지는 수정을 한 단계씩 적용합니다(최대 6단계). 점수에는 위험 항목, 목적 미충족, 원래 조합이 채우던 기능성의 손실, 제품 수, 가격이 들어갑니다. 사용자가 이미 먹는 타사 제품보다 새로 고른 제품을 먼저 조정하고, 고정한 제품은 건드리지 않습니다.

## 데이터 편집 가이드

모든 기준은 `wellink_engine/data/`의 JSON 파일에 있습니다. 코드를 고치지 않고 이 파일만 수정해도 동작이 바뀝니다. 서버를 시작할 때 데이터를 검증하므로, 없는 성분 ID나 태그를 쓰면 바로 오류 메시지가 나옵니다.

| 파일 | 내용 | 수정 예 |
|---|---|---|
| `ingredients.json` | 성분 마스터: 별칭, 단위, 영양성분 기준치(nrv), 기능성 문구와 태그, 기능성 원료 일일섭취량 | 새 원료 추가, 기능성 문구 갱신 |
| `nutrient_reference.json` | 한국인 영양소 섭취기준(권장·충분·상한섭취량, 연령·성별 구간) | 2025 개정 값 반영 |
| `products.json` | 취급 제품(표시 함량·단위·1회/1일 기준·1일 섭취 횟수, 가격, 섭취 시간, 알레르기, 표시 주의사항)과 타사 제품 예시 | 실제 공급 제품으로 교체 |
| `products.d/*.json` | 추가 제품 파일(자동으로 함께 읽음). `tools/import_products.py`로 CSV에서 생성. `pilot.json`은 초기 실증 후보 제품 | 시판 제품 등록 |
| `goals.json` | 건강 관리 목적 → 기능성 태그 가중치 | 목적 추가, 가중치 조정 |
| `drugs.json` | 약효군과 약 이름·제품명 별칭 | 약 추가 |
| `interactions.json` | 약-성분, 성분-성분, 개인 상태-성분 규칙과 약물로 인한 영양소 고갈 | 자문 약사 검토 결과 반영 |
| `profile_rules.json` | 가족력 → 관련 목적·우선 확인 영양소, 생애주기 규칙 | 항목 추가 |

제품마다 `data_status`(sample=가상, partial=일부 확인 필요, verified=표시사항 확인)를 두고, 확인하지 못한 함량은 성분에 `"estimated": true`(가정값)로 표시합니다. 가정값이 계산에 들어가면 점검 결과에 '함량 일부 가정값' 항목이 함께 나옵니다. 같은 제조시설에서 쓰는 알레르기 원료는 `facility_allergens`로 넣으면 '혼입 가능성(주의)'으로 안내합니다.

데이터를 바꾼 뒤에는 `.venv/bin/python -m pytest -q`로 회귀 테스트를 돌리세요.

## 검수가 필요한 데이터

출시 전에 아래 항목을 원문과 대조해야 합니다(S파트 '성분 정보 오류' 위험 대응).

1. **영양소 기준치**: 2020 한국인 영양소 섭취기준으로 넣었습니다. 2025 개정판과 대조해 갱신해야 합니다. 임신·수유부 부가량은 반영하지 않았고, 대신 상담을 안내합니다.
2. **영양성분 기준치(nrv)와 기능성 문구**: 「식품등의 표시기준」과 「건강기능식품의 기준 및 규격」 원문으로 확인해야 합니다.
3. **기능성 원료 일일섭취량**: 고시형 원료별 범위를 확인해야 합니다. 은행잎추출물은 지표성분 기준이 필요해 현재 범위를 비워 두었습니다.
4. **병용 규칙**: 심각도와 문구를 자문 약사가 검토해야 합니다. 의약품 허가사항(식약처 의약품안전나라)을 근거로 확장합니다.
5. **약 이름 사전**: 실제 처방 빈도가 높은 성분과 제품명을 보강해야 합니다. 인식하지 못한 약은 '확인 필요'로 안내합니다.
6. **제품**: 지금 들어 있는 것은 모두 가상 제품입니다. 실제 공급 계약 제품의 표시사항으로 교체해야 합니다.
7. **나이아신 형태**: 형태 표시가 없으면 니코틴산 기준 상한(35mg)으로 보수적으로 판단합니다. 니코틴산아마이드라면 1,000mg입니다.

## 시판 제품으로 페르소나 검증

시판 제품의 표시 정보를 CSV로 정리해 등록하고, 가상 사용자별로 기대한 추천·점검 결과가 나오는지 자동으로 확인할 수 있습니다. 절차는 [validation/README.md](validation/README.md)를 참고하세요.

```bash
.venv/bin/python -m tools.import_products 내파일.csv --out wellink_engine/data/products.d/market.json
.venv/bin/python -m tools.validate_personas validation/personas.example.json --out validation/report.md
```

## 다음 단계 제안

- **관리 약사 검토 절차**: 인식하지 못한 약·성분(`unknown_drug`, `unknown_ingredient`)은 지금은 '약사 확인'으로만 안내합니다. 플랫폼 관리 약사가 판단하고, 그 결과를 `drugs.json`·`interactions.json`에 반영하는 절차로 보완할 예정입니다.

- **식약처 품목 DB 연동**: 공공데이터포털의 건강기능식품 품목 정보로 타사 제품을 제품명 검색만으로 등록할 수 있게 합니다(사용자 입력 의향 50.2%).
- **2단계 생성형 AI**: 점검 결과(규칙 계산값)를 쉬운 말로 풀어 주는 설명과 질의응답을 붙입니다. 점검 판단 자체는 지금처럼 규칙 기반으로 유지합니다.
- **앱 연동**: 사용자 프로필 저장(민감정보 별도 동의, 암호화), 주문·QR API와 연결합니다.
- **파일럿 지표**: 추천 채택률, 수정안 적용률, 점검 후 조합 변경 비율을 로그로 남겨 추천 가중치를 보정합니다.
